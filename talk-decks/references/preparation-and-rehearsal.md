# Preparing and rehearsing a talk

Read with [../SKILL.md](../SKILL.md). These are defaults to adapt, not rules to impose on a deck the speaker already approved.

## Start with a brief and a plan

Record what the audience already knows, the one thing they should leave able to do or decide, the real speaking time and Q&A allocation, the format, the evidence you plan to use and what is out of scope. Infer what you can from the event page and the speaker's notes before asking.

Propose an outline before generating slides. Each section needs a reason to follow the previous one, its evidence, what the listener gets from it and a time budget. A useful shape for a case study: a concrete problem → the task and how success is judged → the mechanism, worked through → what failed or how it was checked → the scoped result → what the listener can do with it.

## The production sequence

1. Start early for an important talk; a month is not too much.
2. Brain dump, then iterate on the plan with the speaker's past decks and skills.
3. Generate one end-to-end first deck. Story first.
4. Apply the speaker's dictated feedback by slide number, with the reason for each change. Content edits keep the slide order; restructure only when asked.
5. Rehearse while the deck is still rough. Time it and find where the spoken story breaks. Apply the next round of directions in the same thread.
6. Export for the final pass (Google Slides or PowerPoint) with build animations, and check it in the real renderer.
7. Record, watch, listen, refine. Four to ten rehearsals and many listens is normal for a big talk; adapt to the stakes.

Keep every version and the speaker's notes verbatim.

## Speaker notes that help

For each slide: the point for the audience, the source, a short spoken entry, the order to read the visual in, and the transition to the next slide. One exact number when needed, plus a rounded spoken version. Do not write a word-for-word script unless the speaker asks.

Keep the speaker's warmth, humor, real examples and caveats. Do not polish away every aside.

For evidence-heavy slides, show a cropped source, one row, one chart comparison or the relevant lines of code. The full data goes in the notes or a backup slide.

## Fit the format

| Format | Choices |
| --- | --- |
| Short conference talk | One central idea and a few earned takeaways. Budget the opening, method, evidence and close; pick the cuts before rehearsing. |
| Longer case study | Use the extra time for one worked failure and how the audience applies it. |
| Hands-on workshop | Define the runnable outcome and prerequisites, test the setup, plan checkpoints and real participant time, and keep saved outputs in case the network or demo fails. |
| Co-presented session | Credit each person, assign sections, timing and handoffs, and agree who covers what so the two parts don't repeat each other. |
| Remote session | Check the shared window and overlays, use a code font that reads at small sizes, give a short URL next to any QR code, and plan where chat questions fit. |

## Rehearse against a budget

Derive the budget from the real slot. Leave a buffer. If a run is long, remove an optional idea or a duplicate setup before speeding up. A small ledger is enough:

| Section or slide | Planned cumulative time | Actual | What broke | Next change |
| --- | --- | --- | --- | --- |

Rehearse the opening, the hardest explanation and the close on their own, then run the whole talk after any real content change.

## Check claims before they become habits

- Put each result next to its task, baseline, configuration, metric, date and source.
- Refresh prices, rankings, model names and launch status before the talk.
- Scope advice to the situation it was measured in.

## After the talk

Write down what you actually reviewed (transcript span, timestamps, audio, video). For each finding: the observation with its timestamp → the likely effect on the audience (labelled as inference) → the proposed change → how to check it next time. Pick one or two priorities. Log it in `FEEDBACK.md`.
